## 4. Functional Requirements

---

### E1 — In-app Notification Center (Realtime)

#### FR-E1-01: Notification Center UI
- Hệ thống hiển thị icon notification (bell) trên navbar với **badge count = số unread notifications**.
- Click vào icon mở panel/dropdown danh sách notifications theo thứ tự thời gian **giảm dần**.
- Mỗi notification item hiển thị: icon event type, nội dung tóm tắt, request code, timestamp tương đối (e.g. "2 phút trước"), trạng thái read/unread.
- Click vào notification → navigate đến đúng Request detail; notification đó chuyển sang **read**.
- Có action "Mark all as read".
- Có filter: All / Unread.

#### FR-E1-02: Realtime delivery
- Khi có event xảy ra, notification xuất hiện trong panel **mà không cần reload trang**.
- Badge count tự cập nhật realtime.
- Có visual indicator (toast nhỏ hoặc badge animation) khi notification mới đến.

#### FR-E1-03: Event types P0 (MUST)

| Event key | Trigger | Người nhận mặc định |
|---|---|---|
| `request.created` | Request được tạo | OPS_COORDINATOR của tenant (queue) |
| `request.assigned` | Request được assign / re-assign | Assignee mới; người tạo request (optional, xem Q3) |
| `request.status_changed` | Status thay đổi | Người tạo request + assignee hiện tại + watchers |
| `request.commented` | Có comment mới | Người tạo request + assignee + watchers + người đã comment trước |
| `request.mentioned` | @mention trong comment | User bị mention trực tiếp |
| `sla.near_breach` | Còn X phút/% trước SLA deadline | Assignee + OPS_COORDINATOR |

#### FR-E1-04: Watcher / Subscribe
- User có thể "watch" một request để nhận thông báo dù không phải assignee hay creator.
- Assignee + creator tự động watch khi được assign / khi tạo.

### E2 — Email Notifications

#### FR-E2-01: Email gửi khi có event
- Các event P0 ở FR-E1-03 đều có thể trigger email.
- Mặc định: email **bật** cho tất cả P0 events (user có thể tắt trong preferences).
- Gửi **immediate** (không gom digest) cho: `request.assigned`, `request.mentioned`, `sla.near_breach`.
- Cho các event còn lại (`created`, `status_changed`, `commented`): gửi theo **digest** — gom các events trong **5 phút** rồi gửi 1 email tổng hợp per user per request (per PO 2026-03-29).

#### FR-E2-02: Email content tối thiểu
- **Subject:** `[SupportOps] [TENANT_NAME] Event summary — REQUEST_CODE`
- **Body gồm:**
  - Tên tenant, Request code + title
  - Event xảy ra (e.g. "Yêu cầu của bạn đã được assign cho Nguyen Van A")
  - Người thực hiện hành động
  - Timestamp
  - CTA button: "Xem chi tiết" → deep link vào app
  - Footer: link unsubscribe / manage preferences

#### FR-E2-03: Rate limiting / Anti-spam
- Không gửi quá **5 emails / user / giờ** cho cùng 1 request (throttle per user per request).
- **Digest window:** 5 phút — các event `created`, `status_changed`, `commented` trong cùng window gom thành 1 email.
- Immediate events (`assigned`, `mentioned`, `sla.near_breach`) **không** gom digest — gửi ngay.

### E3 — Notification Preferences

#### FR-E3-01: User preferences
- Mỗi user có trang **Notification Settings** (hoặc tab trong Account Settings).
- Có thể bật/tắt **từng event type** × **từng kênh** (in-app / email) độc lập.
- UI dạng bảng: rows = event types; columns = kênh.
- Lưu preferences ngay khi thay đổi (optimistic save + confirm toast).

#### FR-E3-02: Default policy
- Default: tất cả event type = ON cho cả in-app và email.
- Thay đổi default áp dụng cho user mới; không override user đã có settings.

#### FR-E3-03: Tenant-level override *(optional V2, xem Q6)*
- TENANT_ADMIN có thể force-disable một số event cho toàn tenant **(out of scope nếu phức tạp — đánh dấu Q6)**.

### E4 — SLA Policy + Near-breach + Escalation

#### FR-E4-01: SLA policy config
- TENANT_ADMIN / OPS_COORDINATOR có thể cấu hình SLA policy theo **priority** (P1/P2/P3/P4 hoặc Critical/High/Medium/Low — align với V1).
- Mỗi policy: `{ priority, response_time_minutes, resolution_time_minutes }`.
- Cấu hình **cả response time SLA và resolution time SLA** (cả hai đều được track và near-breach riêng biệt — per PO 2026-03-29).
- **⚠️ Migration note:** V1 đã có `SlaPolicy` và `SlaRecord` models trong Prisma schema. Tech Lead phải kiểm tra schema hiện tại và quyết định extend hay migrate; không tạo duplicate models.

#### FR-E4-02: SLA tracking
- Với mỗi request, hệ thống tính và track **hai timer độc lập**:
  - `sla_response_due_at` = created_at + response_time_minutes theo priority
  - `sla_resolution_due_at` = created_at + resolution_time_minutes theo priority
- **SLA clock rules (per PO 2026-03-29):**
  - Mặc định: đồng hồ **chạy liên tục** — không dừng khi status thay đổi.
  - **Ngoại lệ duy nhất:** SLA clock **dừng** khi request ở trạng thái `WAITING_FOR_CUSTOMER`.
  - **⚠️ New status required:** `WAITING_FOR_CUSTOMER` chưa có trong danh sách 10 statuses V1 (`DRAFT → SUBMITTED → TRIAGE → ASSIGNED → IN_PROGRESS → WAITING_EXTERNAL_VENDOR → RESOLVED → CLOSED → REOPENED → CANCELLED`). Tech Lead cần **thêm status này vào workflow** — kiểm tra transition rules và enum trước khi implement.

#### FR-E4-03: Near-breach detection
- Background worker chạy theo interval (e.g. mỗi 1–5 phút) check các request chưa đóng.
- Trigger `sla.near_breach` khi còn **≤ 30 phút** trước deadline (áp dụng cho cả response timer và resolution timer — per PO 2026-03-29).
- Worker check **cả hai timers** cho mỗi request; mỗi timer trigger near-breach riêng biệt (tối đa 2 near-breach notifications per request).
- Mỗi request chỉ trigger near-breach **1 lần** (tránh spam).

#### FR-E4-04: Escalation cơ bản
- Khi `sla.near_breach` trigger: notify assignee + OPS_COORDINATOR (như FR-E1-03).
- Khi SLA **đã breach** (deadline đã qua mà chưa đóng): mark trên ticket UI (badge "SLA Breached"), notify thêm OPS_COORDINATOR.
- V2 **không** tự động reassign (để V2.1).

### E5 — Knowledge Base (KB)

#### FR-E5-01: KB CRUD
- TECHNICIAN, OPS_COORDINATOR, TENANT_ADMIN có thể tạo/sửa/ẩn (soft delete) bài KB.
- EMPLOYEE chỉ được **đọc** bài KB published.
- Mỗi bài KB: `{ title, body (rich text), tags[], category, author, status: draft|published, tenant_id, created_at, updated_at }`.

#### FR-E5-02: KB Search
- Full-text search theo title + body.
- Filter theo category / tag.
- Search results hiển thị snippet.

#### FR-E5-03: KB gắn vào ticket
- Khi trả lời comment trong ticket, TECHNICIAN/OPS có thể tìm và **chèn link bài KB** vào comment.
- (V2.0 không làm auto-suggest; V2.1 xem xét).

#### FR-E5-04: KB isolation
- KB thuộc về tenant; không được đọc chéo tenant.

---

### E6 — Canned Responses

#### FR-E6-01: Canned response CRUD
- OPS_COORDINATOR / TENANT_ADMIN quản lý canned responses.
- Mỗi canned response: `{ title, body (plain/rich text), tags[], category, shortcut (optional), tenant_id }`.

#### FR-E6-02: Dùng canned response khi trả lời
- Khi TECHNICIAN/OPS_COORDINATOR soạn comment, có thể tìm canned response bằng shortcut (e.g. `/greet`) hoặc qua picker UI.
- Nội dung được chèn vào ô soạn; có thể chỉnh trước khi gửi.

#### FR-E6-03: Variables trong canned response
- Hỗ trợ tối thiểu: `{{requester_name}}`, `{{request_code}}`, `{{assignee_name}}`.
- Nếu variable không resolve được → giữ nguyên placeholder (không lỗi).

### E7 — Reporting Dashboard V1

#### FR-E7-01: Core metrics
TENANT_ADMIN / OPS_COORDINATOR xem dashboard với các metric:

| Metric | Mô tả |
|---|---|
| Total requests | Theo trạng thái (Open/In Progress/Resolved/Closed) |
| SLA compliance rate | % requests đóng trước SLA deadline |
| SLA near-breach count | Số request đang near-breach hiện tại |
| Avg. first response time | Thời gian từ tạo đến comment đầu tiên từ staff |
| Avg. resolution time | Thời gian từ tạo đến closed/resolved |
| Volume by priority | Breakdown theo priority |
| Volume by category/service type | Breakdown theo loại request (align V1) |

#### FR-E7-02: Filters
- Date range picker: preset (7 ngày / 30 ngày / 90 ngày) + custom range.
- Filter theo assignee (optional V2, xem Q7).

#### FR-E7-03: Display
- Chart types: bar chart (volume), line chart (trend theo ngày), số lớn (KPI cards).
- Không cần realtime dashboard (refresh thủ công hoặc cache 5 phút là đủ V2).
